# VIP за честь и потерянные поля в собственном пакете v4

Дата: 22.10.2026. Правка: `game.js` (раздел 13e, `CFG.vip`, схема v5),
`index.html` (карточка VIP), `style.css` (`.vip`), `.smoke-test.cjs` (регресс
round-trip и блок 11.9), `.visual-check.cjs` (геометрия и темы VIP),
`.vk-mock-check.cjs` (пин схемы), `assets/moderation/privacy-policy.md` (V1.0 → V1.1),
`assets/moderation/application.md` (§6, §6.4, §7 п.11).

## Дефект

Исходно задача была другая: реализовать VIP по маршруту «честь» из §6.4. Маршрут
требовал двух новых полей в сейве, то есть пакета v5 — и по дороге всплыло, что
**v4 не читает сам себя**.

`unpackCloud()` определял версию четырьмя флагами и читал поля так:

```js
const isV3 = p.length === 23 && n[0] === 3;
const isV4 = p.length === 33 && n[0] === 4;
shares: (isV2 || isV3) ? n[12] : 0,        // ← v4 здесь уже мимо
riskDay: isV3 ? n[15] : 0,                 // ← и здесь
gid: isV4 ? n[23] : 0,
```

С появлением v4 хвост гильдии прочитали условием `isV4`, а два выражения выше
забыли, что они тоже обязаны стали «v4 или новее». Для собственного v4-пакета
`isV2`, `isV3` и `isV4` несовместны: `shares/shareDay/shareN` и восемь полей
риск-раунда распаковывались нулями.

Проверка это не ловила, потому что была поставлена неправильно:

```js
ok(c1.w.NEON.unpack(seen) !== null, 'собственный пакет v4 проходит свою же проверку', seen);
```

`!== null` ловит **отказ** пакета. Нули на месте десяти полей — это не отказ:
`unpack` возвращает осмысленный объект, `sanitize()` их принимает, и весь путь
проходит молча. Пакеты v1, v2 и v3 тестировались с ненулевыми полями и были
здоровы; v4, как текущая версия, собственного сквозного теста не получил вовсе.

## Чем это хуже, чем потеря статистики

`shares` участвует в потолке правдоподобия:

```js
const shareMax = (d.shares || 0) * CFG.share.reward;
return d.clicks * perClickMax + passiveMax + adsMax + shareMax;
```

Обнуление `shares` срезает `shareMax`, то есть уменьшает `plausibleCap()`. А дальше
`sanitize()` делает ровно то, чему его учили:

```js
if (d.total > cap) { d.total = cap; d.coins = Math.min(d.coins, cap); fixes++; }
```

Значит честный игрок, прогресс которого приехал из облака с потерянными репостами,
на следующей загрузке теряет часть баланса и «всего заработано» — без единой ошибки
в консоли, с единственным следом в `S.susp`. Сценарий бытовой: второй телефон,
переустановка VK, вход с другого устройства — то есть `cloudPull()` → `unpackCloud()`.

Замер на боевой сборке HEAD (`git archive HEAD`, стенд на :5175, round-trip
`unpack(pack(S))` по всем полям):

```
shares: 7 → 0        riskWins: 4 → 0
shareDay: 20000 → 0  riskLoss: 1 → 0
shareN: 3 → 0        riskBurned: 300 → 0
riskDay: 20001 → 0   rpIdx: 1 → 0
```

## Что сделано

**Исправление формы, а не трёх выражений.** Кумулятивный предикат вместо перечисления
версий — так, чтобы добавление v6 не требовало вспоминать ни одно условие чтения:

```js
const LEN = { 1: 12, 2: 15, 3: 23, 4: 33, 5: 35 };
const ver = n[0];
if (LEN[ver] !== p.length) return null;      // чужая версия схемы
const has = (min) => ver >= min;
shares: has(2) ? n[12] : 0, ...  gid: has(4) ? n[23] : 0, ...  vipUntil: has(5) ? n[33] : 0
```

Прежняя форма была не ошибкой в одном месте, а отсутствием места: она требовала при
каждой новой версии пройти по всем предыдущим выражениям и поправить каждое. Теперь
новая версия добавляет ровно одну строку в `LEN`.

**Регресс, ловящий класс, а не случай.** Два теста вместо одного `!== null`:

* пакет v4 с **ненулевыми** полями всех предыдущих версий и сравнение `shares`,
  `shareDay`, `shareN`, четырёх полей риск-раунда, семи полей гильдии и рейда;
* сквозной round-trip v5 по всем 33 значимым полям с расшифровкой потерянного:
  `shares: 3 → 0`.

Негативный контроль прогонялся живьём: подмена `has(2)` на `ver === 2` красит три
проверки (`round-trip v5`, `КРИТИЧНО: v4-пакет не потерял репосты`, `облачный пакет
v3 распакован без потерь`). До этой правки ни одна проверка на баг не смотрела.

## VIP: что именно и почему такая форма

`CFG.vip = { cost: 40, days: 7, dailyMs: 30 * 60 * 1000 }`. Статус покупается честью
рейда и каждый календарный день UTC выдаёт 30 минут буста ×2.

Форма награды выведена, а не выбрана по вкусу. `plausibleCap()` считает пассивный
потолок из расчёта **постоянно** включённого ×2:

```js
const passiveMax = d.upAuto * CFG.auto.perLevel * CFG.boost.mult * seconds;
```

Поэтому дополнительные минуты буста в уже посчитанный потолок умещаются, а поднятый
множитель вывел бы честного игрока за границу и отнял бы у него монеты — ровно то,
о чём предупреждает 13c. Отдельно проверено, что клика буст не касается:
`clickPower()` возвращает `CFG.click.base + S.upClick * CFG.click.perLevel` без
множителя, ×2 живёт только в `passiveRate()`.

| Решение | Выведено из |
|---|---|
| награда — время, не множитель и не монеты | `plausibleCap()`, 13c про `boost.mult` |
| обмен чести (`boostCost`/`boostMs`) не тронут | `check-copy [8]`: множества чисел в закрепе сообщества |
| потолок срока = `floor(rdLife / cost) + 1`, а не константа | инвариант «честь не монета», тот же приём, что у `riskBurned ≤ total` |

**Выдача бывает только целой.** Первая версия обрезала дневную выдачу до
`maxBoostAheadMs` и списывала сутки — то есть тихий отъём награды, класс ошибки, от
которого защищаются в `raidRedeemBlock`. Тест поймал это на шаге «до края и ещё раз»:
край уезжает вместе с ходом времени, и выдача проходила на 1 мс. Теперь сутки
списываются, только если целиком помещаются; иначе тик повторяет попытку, а
освобождение края догоняет выдачу. Проверено в обе стороны.

**Идемпотентность по `vipDay`, а не по таймеру.** Тик идёт 5 раз в секунду; без
индекса суток игра отдала бы 30 минут буста каждые 200 мс. Тот же приём, что у
`shareDay/shareN` и `rdRedeemed/rdRedN`.

**Слияние — максимумом, как `boostUntil`.** Сумма плодила бы VIP из ничего, а «у
победителя» теряла бы срок, купленный на другом устройстве. Оба направления закрыты
тестами (3 + 9 суток не стали ни 12, ни 3).

## Побочная находка: `-2` в геометрии

После третьей карточки в «Гильдии» покраснела проверка «карточки не сплющены» — и у
всех трёх карточек, включая две нетронутые. Причиной было не сжатие, а сама формула:

```js
squash: e.scrollHeight - Math.round(e.getBoundingClientRect().height)
```

У карточки с рамкой 1 px по кругу `rect.height` на 2 больше её же `scrollHeight`,
поэтому `-2` — норма, и на HEAD она тоже норма (замерено: 222.344 против 220).
Падение вызывал только пин `cards.length === 2`. Проверка оставлена на `<= 1`,
поднята до трёх карточек, а рассуждение записано в её комментарий — чтобы следующий
не тратил время на тот же поиск.
