# Бумаги встали между push и публикацией

Дата: 22.10.2026. Правка: `package.json` (скрипт `guard`),
`.github/workflows/deploy.yml` (джоба `guards`, `build` → `needs: guards`),
`README.md` (подраздел «Порог бумаг» и абзац о джобе в «Как это
выкладывается»). Код игр, наборы и бумаги не изменялись.

## Что сделано

| Артефакт | Что в нём |
|---|---|
| `npm run guard` | четверо подряд через `&&`: `check:copy`, `check:negctl`, `check:negctl:policy`, `check:kit` |
| джоба `guards` | трое без `check:kit`, сборка `_site` первым шагом, `npm ci` отсутствует |
| `build: needs: guards` | расхождение бумаг блокирует выкладку, а не соседствует с ней зелёным деплоем |
| README «Порог бумаг» | порядок как защита, красный порог как штатное состояние, EOL-локальность, отсутствие хука и `--no-verify` |

До этого коммита `npm run guard` существовал только в плане
(`2026-10-22-action-plan.md:82`) — то есть это был не дрейф прозы, а
нереализованная машина. Между `git push` и живым https-хостингом стояла одна
сборка, которая о бумагах не знает ничего: `application.md`, разошедшийся с
`game.js`, не мешал выложить игру.

## Красный порог — это и есть его работа

Выбор был между двумя конвейерами:

1. `guard` = все четверо, CI = трое до кадра (сделано);
2. `guard` = трое, `check:kit` отдельно руками.

Второй удобнее, и он неверен: смысл порога — не выпускать, пока комплект не
целый. `check:kit` держит `134 ok / 0 fail / 1 ждёт` и выход 1, пока в дереве
нет снятого руками `screen-guild.png`. Локальный порог, который зелёный всегда,
— декорация с открытым финалом, тот же дефект, который разобран в
`2026-10-21-privacy-page.md` на маркерах `{{...}}`. Поэтому `npm run guard`
сегодня красный, и это записано в README как штатное состояние, а не как авария:
он перестаёт быть красным ровно в момент появления кадра, и ни на шаг раньше.

## Сборка перед воротами — не экономия, а условие осмысленности

`check:copy` сверяет числа досье с `_site/` и при отсутствии артефакта печатает
⏳ и **пропускает** эту сверку (`tools/check-copy.cjs:465`). Джоба без шага
сборки была бы зелёной, не померив половину своего предмета. Подтверждение из
лога раннера:

```
Боевой артефакт: /home/runner/work/neonclick/neonclick/_site
✅ _site/ несёт те же числа, что описывает досье
===== ТЕКСТЫ ВИТРИНЫ 270 ok / 0 fail =====
```

`check:kit` на том же пустом месте упал бы (`_site/privacy.html` обязателен), но
его в джобе нет — значит, полагаться на падение соседнего прогона нельзя:
следующий добавленный страж остался бы без этой защиты.

`npm ci` в джобе отсутствует: все четверо живут на `node:fs|path|crypto|
child_process`, jsdom и puppeteer-core на этот шаг не едут.

## Порядок как защита, а не косметика

`check:negctl:policy` единственный из четверых пишет в общее дерево — портит
`assets/moderation/privacy-policy.md` и восстанавливает его, — а `check:kit` и
`check:copy` этот файл читают. Прошлый прогон того же состава вразнобой давал
`2 fail / 2 ждёт` на чистом дереве и расход `privacy.html` с исходником на
символе 596 (`2026-10-22-action-plan.md`). Fail-fast через `&&` убирает и второй
случай: умри мутационный прогон посреди дороги и оставь файл испорченным,
следующий по цепочке ничего в полуиспорченном дереве не измерит. Агрегация
«запустить всех и сложить коды возврата» этой защиты не даёт, поэтому её нет.

## Два пробела, которые план требовал назвать вслух

**EOL.** Проверка окончаний строк живёт только в `check-moderation-kit.cjs:445`
(по выводу `git ls-files --eol`), то есть ровно в том прогоне, которого в CI
нет. Переносить её туда отдельным шагом бессмысленно: Actions делает свежий
checkout на Linux, `* text eol=lf` применяется при распаковке, и `w/crlf` там не
возникает физически. Инцидент 22.10.2026 произошёл на машине владельца, до
коммита: редактор записал файлы корпуса с CRLF, `git status` показывал файл
изменённым, а `git diff` — пустым (`2026-10-22-external-corpus.md`). Значит, EOL
мерится локально и только через `npm run guard` — и это записано явно, иначе
следующий, кто «починит CI», решит, что дыра закрыта джобой.

Эта фаза закрыла абзац о себе же живым примером: первый прогон `npm run guard`
дал по новому отчёту `133 ok / 1 fail / 1 ждёт`, где единственным падением было
`ни один текстовый файл не лежит с CRLF вопреки .gitattributes →
["reports/2026-10-22-phase-d1-gates.md"]` — редактор записал 112 переводов строк
этого файла с CRLF. Поймал его именно `check:kit`, которого в CI нет; джоба
`guards` с её 270 / 63 / 6 проглядела бы это полностью. То есть утверждение
«EOL-страж локален и потому обязан запускаться руками перед коммитом» — не
оговорка, а единственное место, где он вообще работает.

**Хук.** `pre-commit`-хука в репозитории нет: `.git/hooks/` содержит одни
`.sample`, `core.hooksPath` не задан (проверено в этом прогоне). Появляться он
не планируется: клон не приносит исполняемых хуков, поэтому он проверял бы
машину владельца, а не чужую. Любой поставленный локально обходится одним
флагом `git commit --no-verify` — он существует в git по построению. Между push
и живым хостингом стоит `guards`, а не хук.

## Что осталось

Фаза D-2 — один шаг: с появлением `screen-guild.png` добавить `check:kit` в
джобу `guards` тем же коммитом, что и кадр. До этого в джобе трое, и это
записано в её комментарии, а не в память участников.

`check:negctl:policy` 6 ok / 0 fail · `check:kit` 134 ok / 0 fail / 1 ждёт ·
`npm run guard` выход 1 (по замыслу, см. выше).

CI, ран `39901161510`: `Бумаги перед выкладкой` → `Сборка артефакта` →
`Публикация на Pages`, все трое `success`; в джобе ворот те же
270 / 63 / 6 без единого ⏳.

Боевой артефакт не сдвинулся: 6 файлов, 318372 байта, `?v=15536bba` /

Побочное наблюдение, записанное, чтобы не потерялось: первый локальный
`node tools/build-release.cjs` сразу после полного прогона ворот упал на
`syscall: 'rm'` (залитый хэндл файла `_site` после `negctl-policy`, который
пересобирает начисто), второй и третий — выход 0. На Linux-runnere не
воспроизвелось ни разу. Лечится порядком прогонов, а не флагами.
