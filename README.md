# NEON CLICK — VK Mini App

Кликер на чистом HTML/CSS/JS без сборки, фреймворков и бэкенда. Раздаётся как
статика, живёт внутри клиента ВКонтакте как мини-приложение.

## Что публикуется

Боевой артефакт — **пять файлов**, и только они должны лежать на хостинге:

| Файл | Роль |
|---|---|
| `index.html` | разметка; подключает три ресурса ниже с `?v=<hash>` |
| `style.css` | витрина и темы |
| `game.js` | вся игровая логика, античит, сейвы |
| `vk-integration.js` | мост в VK: SDK, реклама, репосты, облако, гильдия |
| `vk-bridge.3.0.2.js` | вендоренный `@vkontakte/vk-bridge` (см. `tools/vendor.json`) |

Всё остальное дерево — внутренняя кухня: наборы проверок (`.smoke-test.cjs`,
`.vk-mock-check.cjs`, `.visual-check.cjs`, `.stress-check.cjs`,
`.release-check.cjs`), эталонные прогоны (`base_*.txt`), материалы заявки в
кабинет VK (`assets/moderation/`, см. «Кабинет VK»), `package.json`,
`tools/`. На хостинг они не попадают **механически**, а не по внимательности:
Pages публикует не ветку, а артефакт, собранный `tools/build-release.cjs`
из allowlist (см. `.github/workflows/deploy.yml`). Это важно, потому что
сайт на Pages открывается всем, даже когда репозиторий приватный.

## Сборка артефакта

```
npm run build:release        # → _site/ (в .gitignore)
```

Сборщик делает ровно три вещи и останавливается, если хоть одна не удалась:

1. **Вырезает отладочный хук.** В репозитории `?debug=1` создаёт `window.NEON`
   (`tap`, `add`, `state`, сдвиг часов, темы) — на нём висят четыре набора
   проверок, поэтому из исходника хук удалять нельзя. В публикуемом файле его
   нет: регион между маркерами `RELEASE-STRIP` убирается целиком, а
   `const DEBUG = …` заменяется на `const DEBUG = false;`. Второе важнее, чем
   кажется: тем же флагом выключается **потолок правдоподобия** в античите
   (`game.js`, `if (!legacyT0 && !DEBUG)`), так что в публикации он активен
   всегда. Постусловия проверяются по готовым байтам (`window.NEON` отсутствует,
   маркеров нет, `node --check` проходит), а не по факту срабатывания регэкспа.
2. **Ставит cache-bust.** Каждому локальному ресурсу в `index.html` добавляется
   `?v=<8 hex>` — первые 8 символов sha256 от конечных байтов файла. Без этого
   WebView VK и кеш Pages держат старую игру после хотфикса. Хэш по содержанию,
   а не по SHA коммита: сборка одного и того же исходника бита в биту одинакова,
   и кеш браузера не сбрасывается впустую.
3. **Сверляет вендор.** `vk-bridge.3.0.2.js` сверяется с `tools/vendor.json`
   по размеру и sha256, из него вырезается ссылка на несуществующий `.map`,
   а `SDK_LOCAL` в `vk-integration.js` проверяется на совпадение с именем файла.

Зависимостей у сборщика нет (только `node:fs/crypto/child_process`), поэтому
серверная сборка не ставит `jsdom` и `puppeteer-core` — они нужны лишь локальным
прогонам.

## Как это выкладывается

`git push` в `main` → GitHub Actions (`deploy-pages`) собирает `_site` и
публикует его на Pages. Источник публикации — **GitHub Actions**, а не ветка:
так Jekyll не трогает файлы, и на сервер не уезжает лишнее. Адрес:
`https://<логин>.github.io/<репозиторий>/`.

Первая настройка (однократно):

```
gh repo create <логин>/<репо> --private --source=. --push
gh api repos/<логин>/<репо>/pages -X POST -f build_type=workflow
```

Приватный репозиторий здесь не косметика: история коммитов хранит наборы
проверок и их эталонные прогоны, а наружу смотрит только собранный артефакт.
Pages на приватном репозитории доступен аккаунтам GitHub Pro/Team; на Free
репозиторий приходится делать публичным — тогда наборы проверок и `base_*.txt`
уезжают в историю вместе с ним, и об этом стоит подумать заранее.

## Проверка

| Набор | Против чего | Пользуется хуком | Что закрывает |
|---|---|---|---|
| `.smoke-test.cjs` | jsdom, файлы репозитория | да | разметка, id и классы, игровая математика, темы, параметры запуска VK |
| `.vk-mock-check.cjs` | Chromium + стенд 5173 | да | сцены VK Bridge: реклама, репосты, гильдия, облако |
| `.visual-check.cjs` | Chromium + стенд 5173 | да | геометрия, хит-тесты, палитры тем, скриншоты |
| `.stress-check.cjs` | Chromium + стенд 5173 | да | нагрузка, правки сейва, виртуальные часы, облако, утечки памяти |
| `.release-check.cjs` | **боевой URL**, без мока | **нет** | чёрный ящик по публикации |

Стенд для первых четырёх: `python -m http.server 5173` (или Live Server в
VS Code — тогда `$env:NEON_BASE = 'http://127.0.0.1:5500'`, переписывать код
наборов не требуется). Пятый набор живёт на **5174** и мерит собранный `_site`:
раньше оба мира претендовали на порт 5173, поэтому поднятый для релизной
проверки стенд глушил стенд разработчика, и три набора вместо внятной ошибки
тонули в молчаливом 15-секундном таймауте. Теперь каждый набор сверяет адрес
префлайтом (`tools/stand-guard.cjs`) и краснеет с названием причины и лечением.

Первые четыре набора требуют хук и потому гоняются **только по дереву
репозитория**: в опубликованной игре хука нет by construction, и это проверяемое
утверждение, а не неудобство. Пятый устроен наоборот — он не знает про `NEON`,
тапает мышью, читает `localStorage` и сеть, и потому единственный работает по
боевому URL:

```
npm run build:release
npm run serve:release                                          # стенд _site на 5174
$env:NEON_BASE = 'http://127.0.0.1:5174'; node .release-check.cjs      # прогон локально
$env:NEON_BASE = 'https://<логин>.github.io/<репо>'; node .release-check.cjs   # по публикации
```

Он закрывает три пробела, которых не видит ни один локальный прогон: реальный
HTTPS-хост вместо 127.0.0.1 (TLS, редиректы Pages, кеш Fastly и относительные
пути на **подкаталоге** `/reponame/`, где `/game.js` уже не существует);
загрузку настоящего `vk-bridge` без предподставленного мока; и состав хостинга
(пять файлов отвечают 200, `package.json`, наборы проверок и `.git` — нет).
Плюс два главных утверждения публикации: `?debug=1` не создаёт `window.NEON`,
а 999999, вписанные в `localStorage` руками, не доживают до HUD.

Эталонный прогон пятого — `base_release.txt`, и он отличается от четырёх других по
природе: те описывают дерево репозитория и меняются, когда подрастёт набор, а этот
фиксирует конкретную выкладку — адрес и три `?v=<hash>` из раздела [8]. Значит,
перезаписывается он не вместе с наборами, а вместе с публикацией: diff двух таких
прогонов показывает ровно то, что уехало на хостинг. Сам `base_release.txt` лежит в
дереве и потому внесён в `FOREIGN` того же прогона — «не уехало» проверяется на нём
самом, а не на слух.

Полный прогон перед выкладкой:

```
npm test                                                # сборка + четыре набора
$env:NEON_BASE = 'https://…'; node .release-check.cjs   # пятый — по публикации
```

## Хотфикс

Правим исходники → `npm test` → `git commit` → `git push`. Версии `?v=` меняются
сами по содержанию файлов. Старый кеш WebView не оставит игрока в промежуточном
состоянии: артефакт выкладывается целым каталогом, поэтому либо все пять файлов
новые, либо ни одного.

## Кабинет VK: что делается руками

1. Создать мини-приложение (dev.vk.com → Мои приложения), получить `vk_app_id`.
   В форме создания обязательно выбрать тип «Мини-приложение», а не «Игра»: это
   разные продукты с разными панелями настроек, и задним числом тип не
   перевыпустить. 20.10.2026 карточка 54836005 оказалась созданной как «Игра» —
   и это обнулило весь пункт 3 ниже, вплоть до его четвёртой проверки: VK
   документально не передаёт играм `vk_group_id` и `vk_viewer_group_role`,
   поэтому вкладка «Гильдия» на игровой карточке не оживает ни при каком
   состоянии кабинета сообщества. Проверка стоит одного взгляда в колонку
   «Тип» таблицы «Мои приложения» и замечена она была только после того, как
   три предыдущие причины были по очереди проверены и сняты.
   Ошибочная карточка не перевыпускается: переключателя типа в настройках нет, и
   единственная починка — карточка правильного типа плюс удаление старой. Обе
   подписи ниже взяты из документации VK, а не из кабинета: dev.vk.com в день
   правки отдаёт 404 и баннер «Технические работы», поэтому первый же доступный
   кабинет обязан сверить их глазами. У игрового типа удаление живёт на странице
   размещения, а не настроек: dev.vk.com → «Приложения» (прямая ссылка
   https://dev.vk.com/admin/apps-list) → NeonClick → «Настройки» → «Размещение» →
   в правом нижнем углу «Удалить приложение». Кнопка доступна только
   создателю (наш вход — «Создатель»), а последствия VK формулирует прямо:
   «Удалённую игру нельзя восстановить. Можно создать новую с другим
   идентификатором» — значит id не освобождается, и в бумагах он не правится, а
   заменяется новым. У мини-приложения путь иной: «Мои приложения → Редактировать
   → Настройки» → блок «Удаление мини-приложения» → «Удалить приложение», затем
   «Удалить» во всплывающем окне.
   Порядок важнее скорости: сначала новая карточка, потом удаление. До её
   появления удаление оставляет нас с нулём карточек, а обратимость у двух
   рычагов разная: «Состояние для пользователей» → Отключено выключает карточку
   на время и включается обратно, «Удалить приложение» — нет. Отсюда же следует,
   что удалять не обязательно: ошибочная карточка, оставленная выключенной, не
   мешает ни новой карточке, ни модерации.
   21.10.2026 вторая карточка зарегистрирована: `54839632`. Тип у неё сверен
   глазами с колонкой «Тип» таблицы «Мои приложения» — «Мини-приложение», ровно
   тем взглядом, которого не хватило абзацем выше. С этой минуты удаление
   ошибочной 54836005 перестало быть риском остаться с нулём карточек и стало
   просто следующим шагом. Сам номер при этом не правится, а заменяется, поэтому
   54839632 вписан везде, где живёт ссылка запуска (п.3 ниже и §1 досье), а
   54836005 сохранился ровно в двух ролях: протокол ошибки и путь к её удалению.

2. Настройки → Размещение → вписать URL публикации в **три** поля: десктоп,
   мобильная версия сайта (`m.vk.com`), мобильное приложение. После этого
   прогнать `.release-check.cjs` с `NEON_BASE` по этому URL.
3. Добавить это же приложение как приложение сообщества `vk.com/club242457640`
   (обложка NeonClick) — иначе вкладка «Гильдия» не оживёт: `vk_group_id` приезжает
   только из папки сообщества. Каноническая ссылка запуска —
   `https://vk.com/app54839632_-242457640` (карточка 21.10.2026). Прежняя,
   `app54836005_-242457640`, канонической не была и не станет: это тип «Игра», и
   дальше по этому файлу она идёт только как протокол, а не как адрес. Минус
   перед id сообщества обязателен:
   сообщество в адресной строке VK пишется с минусом, а мост отдаёт `vk_group_id`
   положительным, и скопированное «как есть» значение даёт битую ссылку
   (`vk-integration.js`, ловушка №1).
   Предварительное условие, которого в этом пункте раньше не было: приложение
   должно вообще появиться в списке установки сообщества. 10.10.2026 экран
   «Управление → Приложения» сообщества club242457640 показал установленный
   VK Донат, каталог сторонних приложений («Перейти в каталог», «Показать все»),
   «Ранее установленные приложения» — VK Донат и «Мои приложения» ровно с одной
   строкой «Принять / Отменить заявки в друзья». Ни NeonClick, ни 54836005 там
   нет, значит «Добавить» нажимать пока некуда: пункт 3 начинается не с кнопки,
   а с четырёх проверок.
   1) Аккаунт. «Мои приложения» сообщества собираются из приложений того
      профиля, который устанавливает. Если dev.vk.com → «Мои приложения» под
      этим входом NEON CLICK не показывает, приложение создано другим
      профилем — и решается оно соавторами/тестировщиками в карточке
      приложения, а не этим экраном.
   2) Сообщество. В списке сообществ этого аккаунта два NeonClick. Экран должен
      относиться именно к 242457640 — тому id, что записан в `CFG.guild.roster`;
      адрес настройки сообщества содержит `club242457640` (или `-242457640`).
      Привязка, закрытая в соседнем сообществе, даёт `vk_group_id`, которого в
      ростере нет, и вкладка «Гильдия» это покажет.
   3) Статус. «Состояние для пользователей» = Выключено (п.5 ниже) и
      непройденная модерация прячут приложение из списков установки; если две
      первые проверки пройдены, а строки всё равно нет — смотреть сюда.
      20.10.2026 проверка пройдена и ничего не объяснила: dev.vk.com → «Мои
      приложения» под входом создателя показывает NeonClick (54836005) со
      статусом «Вкл», то есть ни чужой профиль, ни выключенное состояние вины
      не несут. Карточка подписана «Непроверенное приложение» и «Приложение
      доступно только по ссылке» — это скрытие из каталога, и оно объясняет
      отсутствие строки в сообществе, но не объясняет главный запрет: п.4.
   4) Тип приложения. Причина, которой в этом списке не было, и она перебивает
      остальные три. В той же таблице колонка «Тип» у NeonClick говорит «Игра»,
      а не «Мини-приложение»: это другой продукт, с другой панелью настроек и
      другим набором launch-параметров. Документация VK («Параметры запуска»)
      по обоим параметрам, на которых живёт вкладка, пишет буквально: «Параметр
      не используется в играх» — это про `vk_group_id` и про
      `vk_viewer_group_role`. Значит, сколько раз приложение ни добавляй в
      сообщество, `vk_group_id` в игру не приедет, и вкладка навсегда останется
      на ветке «запуск не из сообщества». Кабинет сообщества здесь бессилен:
      чинится не привязкой, а регистрацией нового приложения типа
      «Мини-приложение» на тот же опубликованный URL. Рантайм id не хранит —
      `appLink()` и `guildLaunch()` читают `vk_app_id` из launch-параметров, —
      поэтому ни пересборки, ни нового деплоя замена не требует; меняется только
      ссылка запуска в этом файле и в досье.
      21.10.2026 регистрация состоялась, и проверка прошла на новой карточке: в
      той же таблице рядом со строкой 54836005 лежит 54839632 с колонкой «Тип»
      «Мини-приложение». Этим снята четвёртая причина — единственная из четырёх,
      которая снимается регистрацией. Первые три на 54839632 не сняты и сняться
      регистрацией не могут: карточка свежая, в списке установки сообщества её
      ещё нет, а «Состояние для пользователей» у неё выключено по умолчанию.
      Значит, порядок пункта 3 на новой карточке тот же — четыре проверки, и
      только потом «Добавить».
   Из репозитория это не проверяется: `vk.com/club242457640`,
   `vk.com/public242457640`, `vk.com/app54839632` и прежний `vk.com/app54836005`
   анонимно отдают 200 с формой входа, поэтому ни имя сообщества, ни владельца
   приложения по сети не разделить — все четыре проверки делаются только
   залогиненным глазом.
   Кнопка действия сообщества остаётся ВЫКЛЮЧЕННОЙ («Показывать кнопку действия»
   — нет). Дело не в ярлыке: единственный тип, который мы видели в кабинете, —
   «Открыть мобильное приложение», и он не сохраняется без хотя бы одной ссылки
   на стор (кабинет отвечает «Укажите хотя бы одну ссылку» на пустые App Store /
   Google Play / RuStore; проверено 10.10.2026). Ссылок на сторы у проекта нет и
   быть не может: нативного пакета нет, есть пять статических файлов в WebView
   клиента VK. Поле «URL-схема» принимает при этом схему вида `myapp://` — по ней
   ОС открывает уже установленный пакет, — а не https-ссылку, так что класть
   туда ссылку запуска бессмысленно вдвойне. Подойдёт любой иной тип, после
   выбора которого поля URL-схемы и сторов не появляются: критерий
   поведенческий, потому что ярлык правильного типа по документации не сверян
   (dev.vk.com недоступен).
   Кнопка не определяет гильдию: `vk_group_id` даёт добавление приложения в
   сообщество, а не настройка обложки, и ссылка запуска выше работает сама по
   себе. Если тип для мини-приложения в списке найдётся, текст кнопки — «Играть»:
   называет действие и не обещает выигрыш. Внутри игры кнопка ва-банка подписана
   «Поставить» — она ставит, а не играет, и это тот же запрет на обещания, что и
   для текстов витрины (`npm run check:copy`, группа [7]).
   Симптом отсутствующей привязки виден прямо в адресной строке: переход по
   `app54836005_-242457640` открывается как `app54836005`, суффикс `_-242457640`
   срезается, и `vk_group_id` в игру не приезжает. Это не редирект домена:
   анонимный HTTP-запрос по тому же адресу суффикс сохраняет
   (302 → `m.vk.com/app54836005_-242457640`, десктопный UA получает 200 на
   исходном URL) — срезает его клиент VK, маршрутизируя незакрытую привязку на
   личную страницу приложения. Вкладка «Гильдия» на таком запуске подписывает
   причину правильно: «запуск не из сообщества». «Нет подключения к VK» значит
   только одно — моста нет вовсе (страница открыта вне VK), и смешивать эти две
   ветки нельзя: в первой игрок подключён к VK, и лечится он пунктом 3, а не
   переподключением.
   Этот контроль снят на старой карточке и на новой ещё не повторён, а повторять
   его обязан каждый, кто меняет карточку. Замер 21.10.2026: анонимный запрос по
   `https://vk.com/app54839632_-242457640` отвечает 200 и редиректа не делает —
   ровно как запрос по прежнему адресу `app54836005_-242457640`. Сервер суффикс
   не режет ни там, ни там, а запись про 302 на `m.vk.com` держит в бумагах
   вывод, а не цифру статуса: она зависела от обстоятельств того замера (UA и
   куки). Живое наблюдение остаётся одно: суффикс срезает клиент VK, и видно его
   только в адресной строке открытого приложения. Пока переход по
   `app54839632_-242457640` остаётся `app54839632_-242457640`, пункт 3 на новой
   карточке не закрыт и кадр «Гильдии» с неё не снимается.
4. Подключить кабинет VK Ads и оформить точки монетизации: rewarded-ролик
   (`VKWebAppShowNativeAds` с `ad_format: 'reward'`) и репост. Пока кабинет не
   подключён, `VKWebAppCheckNativeAds` отвечает пусто и точка наград остаётся
   неактивной — игра при этом не ломается, это штатная ветка.
5. Держать «Состояние для пользователей» = Выключено, пока идёт обкатка: по
   умолчанию приложение видно только создателю и администраторам по
   `vk.com/app{ID}`; для проверки на чужом телефоне добавляем тестировщиков в
   разделе «Тестирование». Включать перед модерацией.
6. Собрать материалы модерации: `npm run assets:moderation` → `assets/moderation/`
   (`icon-512.png`, `icon-192.png` — загрузить в кабинет; `screen-neon.png`,
   `screen-meme.png`, `screen-sat.png`, `screen-bonus.png` — скриншоты). Иконка и
   кадры генерируются из настоящего `style.css` и боевого артефакта, а не рисуются
   отдельно, и каждый файл проходит постусловия (геометрия диска, различимость тем,
   отсутствие ошибок страницы). Скриншотов вкладки «Гильдия» там нет намеренно: вне
   реального запуска из папки сообщества (п.3) она показывает служебное состояние,
   и такой кадр на модерации выглядит как сломанный экран — снять его нужно вручную
   уже после п.3. Не производит генератор, но в комплект входит текстовая часть:
   `privacy-policy.md` (политика конфиденциальности) и `application.md` (досье
   заявки: категория, возрастной ценз, описания для витрины, чек-лист отправки).
7. Проверить комплект бумаг: `npm run check:kit`. Скрипт сверяет каждое
   содержательное утверждение обоих документов с `game.js` и `vk-integration.js` —
   ключи хранилища, лимиты облака, вызываемые и отказанные методы моста, домены
   артефакта, признаки категории и возраста. Ничего не запускает, зависимостей не
   требует и в `npm test` не входит намеренно: он отвечает на вопрос «можно ли
   отправлять», а не «работает ли игра», и краснеет по маркерам `{{...}}`, которые
   закрывает только человек. Вешать его в сборку значит сделать зелёный прогон
   недостижимым до последнего дня. Тот же прогон с
   `NEON_KIT_DISTORT=keys|methods|domain|reset|foreign|geom|limit` обязан падать:
   проверка, которая не краснеет на битых данных, декоративна.
8. Проверить тексты витрины (§4 досье): `npm run check:copy`. Прогон отдельный,
   потому что отдельный и предмет: длина трёх полей описания, каждое число в тексте
   против `CFG` игры, исходники против `_site/` и слова против правил выбранной
   категории. Тот, кто правит баланс, почти никогда не правит описание — и именно
   так витрина начинает врать незаметно от коммита.

## Известные ограничения

- **Идентификаторы читаются через `parseInt`** (`vk-integration.js`:
  `vk_group_id`, `group_id`, `gid`). Пока VK привозит числа — всё в порядке.
  Переход на LongID, о котором предупреждает VK, означает, что нечисловой id
  даст `NaN → 0 → guildLaunch() === null`, и вкладка «Гильдия» тихо исчезнет.
  Монетизация от этого не пострадает, но замечать такое надо по факту, поэтому
  пункт здесь.
- **Подпись сейва клиентская** (`SIGN_SALT` в `game.js`). Она отрезвляет ручную
  правку и копит «подозрительность», но не может быть криптозащитой для того, у
  кого есть доступ к байтам игры. Серверной проверки прогресса нет намеренно:
  бэкенда в этом проекте нет вообще.
- **Домены `vk.ru` и `m.vk.ru`.** VK советует добавлять их в доверенные, если
  приложение проверяет происхождение запросов. Мы не проверяем ничего
  (`origin` в релизных файлах встречается только как CSS `transform-origin`),
  поэтому оба домена работают из коробки.
- **Приватный режим WebView** режет `localStorage`: все обращения к нему в
  `game.js` обёрнуты в `try/catch`, а прогресс дублируется в облако VK
  (`VKWebAppStorageSet/Get`, лимит 4096 символов на значение).

## Отчёты

Законченные разбирательства живут в `reports/` и в руководство не попадают:
`reports/2026-10-20-guild-type.md` — протокол поиска причины мёртвой гильдии за
20.10.2026. Дело не в гигиене, а в стороже `tools/negctl-copy.cjs`: повторённые
в руководстве цитата документации или ярлык типа делают правило истинным и после
вырезания абзаца, которое оно сторожит, — то есть мёртвым. Отсюда порядок:
руководство держит только то, что делается руками, а как это было найдено — отчёт.
